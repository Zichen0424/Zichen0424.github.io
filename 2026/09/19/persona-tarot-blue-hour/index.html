BLUE HOUR：用 React 做一个 Persona 3 风格的塔罗网站

Created2026-09-19|Updated2026-09-19|项目实践
|Post Views:

我做了一个以《女神异闻录 3》蓝白视觉为灵感的塔罗网站，叫作 BLUE HOUR · 蓝色时刻。

它包含 22 张大阿尔卡纳、六种牌阵、逐张选牌与揭晓、塔罗图鉴，以及保存在浏览器里的历史记录。整个项目使用 React、TypeScript 和 Vite，不需要后端、账户或 API 密钥。

这篇文章想聊聊，游戏界面的氛围如何落到网页实现上，以及抽牌、动画和本地存储背后的几个具体设计。

项目源码：PersonaTarot

从视觉风格到交互节奏

蓝白配色、大字号窄体英文、斜向菜单和几何构图，构成了网站的主要视觉语言。但只有颜色和背景，还不足以撑起完整体验。

进入页面后，用户会先看到牌阵示意，再经过洗牌、选牌、翻面，最后阅读结果。页面不同阶段的信息量和动效也随之变化：选牌时突出可操作的牌背，揭晓时把注意力集中到已选卡牌，完成后才展开解释。

项目使用 React 19、TypeScript 5.9 和 Vite 7。牌面由 SVG 绘制，动画主要通过 CSS 实现，没有引入额外的动画库或全局状态管理库。英文字体 Barlow Condensed 随项目打包，中文使用系统字体。

这里也需要区分两类参考：P3 提供了视觉灵感；六种牌阵的菜单与牌位则参考了提供的演示素材，并对照《明日方舟》“今日答案！”活动资料整理，并非 P3 原作中的塔罗玩法。

六种牌阵，共用一套数据和流程

当前开放的六种牌阵分别是：

牌阵 中文名 牌位
THE FLOW 时间之流 过去、现在、未来
THE GUN 铳与手 行动、方式、目标、反应
THE CREPE 饼与馅 表象、内情、感触、余存
THE GATE 此与彼 彼在、此在、通行、开启
THE HALO 本真之环 输出、输入、处理、内核、记忆
DAILY READING / THE COIN 正与反 所得、所失

这些模式定义在 src/data/tarot.ts 中。每个模式包含名称、牌位、提示语和总结，抽牌数量直接来自 positions.length。

这样，三张牌和五张牌不需要分别维护两套逻辑。选满多少张才能进入揭晓阶段、结果页显示多少个位置，都读取同一个配置。

牌库也采用统一结构：每张牌包含编号、中英文名称、罗马数字，以及正逆位的关键词、基础牌义、行动建议和模式解读。

结果页按“牌 → 正逆位 → 模式”读取文本，再结合对应牌位的提问展示。当前部分模式的解读由模式引导语与基础牌义组合，并不是每一种组合都独立撰写了一整套长文。

用户输入的问题只用于记录和回看，不会发往服务器，也不参与答案生成。这是一个以预写牌义辅助自我思考的应用。

用状态机约束抽牌过程

抽牌流程涉及多个阶段。如果分别用“正在洗牌”“可以选牌”“已经结束”等布尔值描述，很容易产生互相矛盾的组合。

每一种操作都有前置条件。例如，只有 selecting 阶段才能选牌；索引必须有效，且不能已经被选中。选中的牌数达到当前牌阵要求后，才能进入 revealing。

翻牌和完成操作同样受到限制。只有全部揭晓后，应用才创建记录并保存；重复点击和不符合阶段的操作会被忽略。

这种做法让界面和业务规则分开：按钮是否禁用属于界面反馈，状态转换是否合法则由 reducer 再检查一次。即使发生快速点击，流程仍然有明确的约束。

每张牌的正逆位也在生成牌组时确定，以 0.5 为阈值。

因此，用户面对的 22 张牌背，对应的是已经生成好的完整牌组。点击只是选取位置，不会在每次点击时临时抽一张新牌；无重复牌也由“完整牌库打乱后再选择”自然保证。

shuffleDeck 还允许传入自定义随机函数。测试时可以固定返回值，验证正逆位阈值和边界索引，不必依赖碰运气触发特定情况。

SVG 牌面：统一卡框，独立图案

牌面拆成两个主要组件：

  • CardArt.tsx：绘制卡框、渐变、牌背、编号与名称。
  • ArcanaSymbol.tsx：按牌编号绘制不同的几何图案。

所有卡牌共用 viewBox="0 0 240 400"，所以抽牌区、结果页和图鉴可以复用同一个组件，只改变显示尺寸。

这里有一个容易忽略的细节：SVG 的渐变和图案通过 ID 引用。当同一页面出现多张牌时，如果每个实例都使用相同 ID，就可能引用到别的卡牌资源。

项目使用 React 的 useId() 生成实例标识，再用于 <linearGradient>、<pattern> 和对应引用，避免这种冲突。

几何牌面由项目自行绘制；背景中的 P3 角色素材与牌面不是同一种来源，素材归属在仓库的 CREDITS.md 中单独说明。

圆形波纹：动画也要处理取消和竞争

页面背景分成两组：五个 THE 牌阵共用一组，DAILY READING 使用另一组。

THE 系列内部切换时保持背景静止，只播放约 540 毫秒的牌面翻转，并给不同卡牌加入少量延迟。只有在 THE 和 DAILY 之间切换时，才播放约 2.2 秒的圆形扩散。

SceneBackground.tsx 同时维护当前背景 base 和即将进入的背景 incoming。新背景放在上层，通过 CSS 的 clip-path: circle(...) 从接近中央的位置逐步展开，三层淡色圆环补充波纹边缘。

扩散半径也不是写死的。组件使用 ResizeObserver 测量容器，根据宽高计算足以覆盖最远角落的半径，避免在较高的手机页面上留下未覆盖区域。

动画的另一半工作是处理用户打断：

  • 背景先预加载，再开始展开。
  • 切换目标变化时，清理旧计时器。
  • 异步加载完成后，检查该次操作是否已取消。
  • 快速反向切换时，直接收敛到最后选择的场景。
  • 关闭动效或启用系统减少动态效果时，直接更新背景。

这些处理保证了动画结束后的画面与当前选择一致，不会被较早的回调改回旧场景。

每日结果和历史记录为什么分开保存

本地存储以 blue-hour:v1 为键，主要保存两部分：

history 保留最近 30 条完成记录；daily 单独保存每日结果。

分开保存的原因很直接：清空历史不应该让当天的每日结果重新抽取。普通记录不断增加、旧记录被挤出列表，也不应该影响当天指引。

“今天”使用设备本地年月日计算，而不是截取 UTC 时间字符串。页面还会定时检查日期，并在窗口重新获得焦点或可见性变化时更新日期状态。

这里的固定结果依赖浏览器存储，不是由日期作为种子重新计算出来的。同一浏览器保留存储时，可以恢复当天结果；清除站点数据、换浏览器或存储不可用时，就不能保证延续。

加载记录时，程序也不会只做一次 JSON.parse 就直接信任数据。它会检查模式、牌数、牌编号、正逆位、文本长度和重复卡牌，再过滤无效记录。

旧版模式仍保留对应定义，尤其是旧版“每日一牌”。如果当天已经保存一张牌的旧结果，就继续显示原结果，不会强行补成新版两张牌。

手机布局与键盘操作

桌面上的斜向大字菜单，在手机上改为横向菜单；结果牌阵也随屏幕宽度调整。

固定底栏则采用实际测量高度的方式：React 用 ResizeObserver 把底栏高度写入 CSS 变量 --app-footer-height，内容区按这个数值预留底部空间。这样，手机上文字换行导致底栏变高时，也不会压住最后一段内容。

交互还包括方向键选牌、阶段切换后的焦点移动，以及用原生 <dialog> 展示历史记录。

这些细节让视觉表现较强的页面仍然可以通过键盘完成主要操作。

测试和静态部署

项目的 Vitest 测试主要覆盖抽牌与存储规则，包括完整牌库、六种牌阵的牌数、不重复选牌、正逆位阈值、非法状态操作、每日日期边界，以及损坏存储和旧记录兼容。

构建执行 tsc -b && vite build，先做 TypeScript 检查，再生成静态文件。

部署工作流把测试构建与发布分开：先运行 npm ci、测试和构建，再上传 dist，最后通过 GitHub Pages 官方部署 Action 发布。测试或构建失败，发布任务就不会继续。

路由使用哈希形式，例如 #/atlas/9；Vite 设置 base: './'，使构建资源使用相对路径。这两处配置让网站可以部署到仓库子目录，无需额外配置前端路由重写。

下一步可以继续打磨什么

当前版本已经把视觉界面、抽牌流程和本地记录连接起来。继续迭代时，我会优先考虑两个方向。

一是丰富不同牌阵的解读，让它们不只是在基础牌义前增加不同的引导语，而是更贴合对应问题结构。

二是增加浏览器端的自动化交互测试。现有测试更集中在数据和状态逻辑；快速切换场景、跨午夜恢复每日结果、手机底栏布局等行为，仍值得单独验证。

这个项目里让我最感兴趣的，是如何让强烈的视觉风格与清晰的交互规则配合起来：牌面负责表达，状态机约束过程，动画承接变化，本地记录让一次体验可以被回看。
